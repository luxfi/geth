# Lux Geth

Lux Geth is a high-performance fork of go-ethereum (Geth) optimized specifically for the Lux blockchain network. This implementation features enhanced database backends, post-quantum cryptography support, and improved consensus mechanisms.

## Overview

Lux Geth is a high-performance fork of go-ethereum specifically optimized for the Lux blockchain ecosystem. It serves as the execution layer implementation for Lux's C-Chain (Contract Chain), providing full EVM compatibility while incorporating significant enhancements in database performance, post-quantum cryptography, and consensus integration.

### What Makes Lux Geth Different

**1. Native Multi-Database Support**
- First-class support for BadgerDB with 85K+ writes/sec performance
- PebbleDB integration for balanced workloads
- Seamless database migration tools

**2. Post-Quantum Ready**
- NIST FIPS-compliant quantum-resistant algorithms (ML-DSA, ML-KEM, SLH-DSA)
- Hybrid classical/post-quantum signature schemes
- Smart contract precompiles for PQ operations

**3. Lux Network Integration**
- Native plugin system for Lux consensus engine
- Cross-chain messaging support
- Validator management and uptime tracking
- Dynamic fee adjustments optimized for Lux

**4. Enhanced State Management**
- Path-based state storage for improved efficiency
- Advanced pruning with parallel processing
- Snapshot acceleration for faster sync

**5. Enterprise Features**
- Comprehensive Prometheus metrics
- Multiple database backend options
- Production-grade configuration templates
- Extensive RPC API extensions

## Key Features

### Performance Enhancements
- **BadgerDB Integration**: High-performance key-value store with better write performance than LevelDB
- **PebbleDB Support**: Modern RocksDB-inspired storage engine with improved compaction
- **Optimized State Management**: Enhanced state pruning and caching mechanisms
- **Parallel Transaction Processing**: Improved throughput for high-volume networks

### Post-Quantum Cryptography
- **ML-DSA (Dilithium)**: FIPS 204 compliant quantum-resistant signatures
- **ML-KEM (Kyber)**: FIPS 203 compliant key encapsulation
- **SLH-DSA (SPHINCS+)**: Hash-based signatures for long-term security
- **Hybrid Signatures**: Support for both classical and post-quantum signatures

### Lux-Specific Modifications
- **Custom Genesis Configuration**: Lux network-specific parameters
- **Modified Gas Economics**: Optimized for Lux's fee structure
- **Enhanced RPC APIs**: Additional endpoints for Lux-specific operations
- **Cross-Chain Communication**: Native support for Lux's multi-chain architecture

### Database Backends
- **BadgerDB**: Default backend for optimal performance
- **PebbleDB**: Alternative modern storage engine
- **LevelDB**: Legacy support for compatibility
- **MemoryDB**: In-memory option for testing

## Quick Start

### Installation

```bash
# Clone the repository
git clone https://github.com/luxfi/geth
cd geth

# Build the binary
make geth

# Or build all tools
make all
```

### Running a Node

```bash
# Start with default configuration
./build/bin/geth

# Start with custom data directory
./build/bin/geth --datadir /path/to/data

# Start with Lux mainnet configuration
./build/bin/geth --networkid 1 --lux-mainnet

# Start with BadgerDB (default)
./build/bin/geth --db.engine=badger

# Start with PebbleDB
./build/bin/geth --db.engine=pebble
```

### Database Configuration

#### BadgerDB (Default - Optimized for Lux)
```bash
# BadgerDB with optimal settings
--db.engine=badger
--db.badger.truncate=true
--db.badger.compactL0OnClose=true
--db.badger.valueLogFileSize=1073741824  # 1GB
--db.badger.valueLogMaxEntries=1000000
--db.badger.numMemtables=5
--db.badger.numLevelZeroTables=5
--db.badger.numLevelZeroTablesStall=10
--db.badger.levelOneSize=268435456       # 256MB
--db.badger.valueTreshold=1024           # 1KB
```

**BadgerDB Performance Characteristics:**
- Write Speed: ~85,000 ops/sec
- Read Speed: ~200,000 ops/sec
- Compression: Built-in Snappy/ZSTD
- Memory Usage: Configurable LSM tree
- Best For: High write throughput, large datasets

#### PebbleDB (Alternative - RocksDB-inspired)
```bash
# PebbleDB configuration
--db.engine=pebble
--db.pebble.cache=512                    # MB
--db.pebble.handles=500
--db.pebble.compaction.concurrency=3
--db.pebble.memtable.size=64             # MB
--db.pebble.max.open.files=1000
--db.pebble.block.size=4096
--db.pebble.filter.policy=bloom:10
```

**PebbleDB Performance Characteristics:**
- Write Speed: ~70,000 ops/sec
- Read Speed: ~150,000 ops/sec
- Compression: Snappy by default
- Memory Usage: Efficient caching
- Best For: Balanced read/write, stable performance

#### LevelDB (Legacy - Compatibility)
```bash
# LevelDB configuration
--db.engine=leveldb
--db.leveldb.cache=768                   # MB
--db.leveldb.handles=1024
--db.leveldb.compaction=8
--db.leveldb.writebuffer=32              # MB
```

**LevelDB Performance Characteristics:**
- Write Speed: ~50,000 ops/sec
- Read Speed: ~100,000 ops/sec
- Compression: Snappy
- Memory Usage: Moderate
- Best For: Compatibility, smaller datasets

#### Database Selection Guide

| Use Case | Recommended | Rationale |
|----------|-------------|-----------|
| Validator Node | BadgerDB | Optimal write performance for block production |
| Archive Node | PebbleDB | Balanced performance for historical queries |
| Light Client | LevelDB | Lower resource usage |
| Development | MemoryDB | Fast iteration, no persistence |

## Performance Optimization

### State Management Enhancements

Lux Geth includes advanced state management optimizations:

#### Path-Based State Scheme
```bash
# Enable path-based storage (more efficient than hash-based)
--state.scheme=path
--state.history=90000     # Keep 90k blocks of history
--state.cache=4096        # 4GB state cache
```

#### Advanced State Pruning
```bash
# Full pruning configuration
--state.pruning=full
--state.pruning.memory=1024      # MB for pruning operations
--state.pruning.threads=4        # Parallel pruning threads
--state.pruning.interval=3600    # Prune every hour

# Garbage collection tuning
--cache.gc=25             # GC when cache is 25% full
--cache.trie=15           # Trie cache percentage
--cache.trie.journal=/path/to/journal  # Persistent trie journal
--cache.trie.rejournal=1h        # Rejournal interval
--cache.snapshot=10       # Snapshot cache percentage
```

## Post-Quantum Features

### Supported Algorithms

Lux Geth implements NIST-standardized post-quantum algorithms:

#### ML-DSA (Module-Lattice Digital Signature Algorithm - FIPS 204)
- **ML-DSA-44**: 128-bit security level, ~2.4KB signatures
- **ML-DSA-65**: 192-bit security level, ~3.3KB signatures (default)
- **ML-DSA-87**: 256-bit security level, ~4.6KB signatures

#### ML-KEM (Module-Lattice Key Encapsulation - FIPS 203)
- **ML-KEM-512**: 128-bit security, 768-byte ciphertext
- **ML-KEM-768**: 192-bit security, 1,088-byte ciphertext
- **ML-KEM-1024**: 256-bit security, 1,568-byte ciphertext

#### SLH-DSA (Stateless Hash-Based Signatures - FIPS 205)
- **SLH-DSA-128s**: 128-bit security, small signatures
- **SLH-DSA-192s**: 192-bit security, small signatures
- **SLH-DSA-256s**: 256-bit security, small signatures

### Enabling Post-Quantum Signatures

```bash
# Enable PQ crypto with specific algorithm
--pq.enabled=true
--pq.algorithm=ML-DSA-65
--pq.hybrid=true

# Configure hybrid mode (classical + PQ)
--pq.hybrid.classical=secp256k1
--pq.hybrid.postquantum=ML-DSA-65

# Enable signature caching for performance
--pq.cache.size=10000
--pq.cache.ttl=1h
```

### Quantum-Safe Transaction Example

```go
import (
    "github.com/luxfi/geth/crypto"
    "github.com/luxfi/geth/core/types"
)

// Create quantum-safe transaction
tx := types.NewTransaction(
    nonce,
    to,
    value,
    gasLimit,
    gasPrice,
    data,
)

// Sign with ML-DSA-65
signer := crypto.NewMLDSASigner(crypto.AlgoMLDSA65)
signedTx, err := signer.SignTx(tx, privateKey)

// Verify signature
valid, err := crypto.VerifyMLDSA(
    signedTx.Hash().Bytes(),
    signature,
    publicKey,
)

// Hybrid signing (classical + PQ)
hybridSigner := pqcrypto.NewHybridSigner(
    pqcrypto.AlgoHybridSecp256k1MLDSA,
)
hybridTx, err := hybridSigner.SignTx(tx, classicalKey, pqKey)
```

## Migration Guide

### From go-ethereum

1. **Database Migration**:
```bash
# Export from go-ethereum
geth export chaindata.rlp

# Import to Lux Geth
./build/bin/geth import chaindata.rlp --datadir /new/path
```

2. **Configuration Changes**:
- Replace `subnet` with `net` in configurations
- Update chain ID to Lux network values
- Configure Lux-specific RPC endpoints

3. **API Adjustments**:
- Use `lux_*` prefixed methods for Lux-specific features
- Standard `eth_*` methods remain compatible

### Common Issues

```bash
./build/bin/geth db repair --datadir /path/to/data

./build/bin/geth db rebuild-state --datadir /path/to/data
```

```bash
# Reset to specific block
./build/bin/geth rollback --block 12345

# Clear pending transactions
./build/bin/geth txpool clear
```

#### Performance Problems
- Check disk I/O: `iostat -x 1`
- Monitor memory: `free -h`
- Review cache settings
- Consider switching database backend

### Lux Plugin System

The Lux Geth fork includes a plugin system for integration with the Lux node:

#### Plugin EVM Package (`/plugin/evm`)
```go
// VM interface implementation for Lux consensus
type VM struct {
    backend     *eth.Ethereum
    validators  *validators.Manager
    uptime      *uptime.Manager

// Core VM functions
func (vm *VM) Initialize(
    ctx context.Context,

    genesisBytes []byte,
    upgradeBytes []byte,
    configBytes []byte,
    toEngine chan<- common.Message,

func (vm *VM) BuildBlock(ctx context.Context) (chain.Block, error)
```

#### Validator Management (`/plugin/evm/validators`)

#### Block Integration (`/plugin/evm/block.go`)
- Implements Lux consensus block interface
- Handles block verification and acceptance
- Manages state transitions during consensus
